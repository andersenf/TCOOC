# S0-6: Connect the AWS account (secure access, bootstrap, OIDC, budget)

**Epic:** Sprint 0 foundations · **Size:** M · **Owner:** Developer (design: Architect; access and budget: product owner) · **Status:** Backlog
**Requested by:** product owner

**Dependencies:**
- **S0-2 / ADR-004** (revised, approved by the product owner, D-10): one AWS account, `prod` stage only, region `eu-west-1`, CI auth model.
- S0-3 Part A (a CDK app with a "hello" stack and a CI workflow to run it).
- Product owner supplies: the AWS account (D-01, resolved 2026-11-23) and the `tco-cars` CLI profile for an admin IAM user (D-13), GitHub repo owner/name (D-04), budget alert email (D-05) and budget thresholds (D-07).
**Blocks:** S0-3 Part B (deploy step in CI).

## Story
As the Developer, I want working local access (the `tco-cars` profile, D-13) and a CI deploy path to the AWS account, so that changes normally reach `prod` through GitHub Actions from `main`, CI holds no long-lived keys, and any local deploy before v1.0.0 follows the ADR-004 rules.

## Acceptance criteria
- **No long-lived keys.** Given the repo and the CI configuration, When they are searched (including git history and GitHub Actions secrets), Then there are no long-lived AWS access keys or secret keys; the only AWS-related values are non-secret identifiers (account ID, region, role ARN) as decided in ADR-004.
- **Local access with the `tco-cars` profile (D-13).** Given the product owner's machine with the `tco-cars` CLI profile, When an agent uses it (directly or through the `aws-mcp` server), Then `aws sts get-caller-identity --profile tco-cars` returns the expected account, and `cdk diff` and `cdk deploy` for the `prod` stage run successfully from it. There is no read-only denial test before v1.0.0. The setup steps are documented in the repo (e.g. `docs/runbooks/aws-access.md`).
- **Local deploy rules.** Given the runbook and ADR-004 section 4, When they are read, Then they state that CI from `main` is the normal deploy path, that local deploys run only through the `deploy-local` wrapper from a clean tree at a pushed commit, and that CI redeploys `main` after any local deploy; and the wrapper refuses to deploy from a dirty tree or an unpushed commit.
- **Bootstrap done once.** Given the `tco-cars` profile, When the one-time `cdk bootstrap` is run following the runbook, Then it succeeds. Switching agent access to read-only and retiring or restricting the admin user is on the ADR-004 v1.0.0 checklist, not in this story.
- **Region bootstrapped once.** Given region `eu-west-1` from ADR-004, When `cdk bootstrap` has run once for the single account, Then the CDK bootstrap stack exists in `eu-west-1` only, and no resources are created outside the EU (except global services CloudFront needs).
- **Branch protection on `main`.** Given the GitHub repo, When branch protection (or a ruleset) is set on `main`, Then merging needs a pull request with all required checks passing, and direct pushes to `main` are rejected. This is in place before the first automatic deploy to `prod`.
- **OIDC with least privilege.** Given the GitHub repo owner/name, When the GitHub Actions OIDC identity provider and roles are created, Then there is one CI deploy role for `prod` whose trust policy only allows that repo on `main` (as set in ADR-004), with permissions limited to what CDK deploy needs (assuming the CDK bootstrap roles), not `AdministratorAccess`; and a read-only role that pull-request workflows can assume to run `cdk diff`, which cannot deploy or change resources.
- **OIDC is denied for others.** Given a workflow run from a fork, another repo or a non-allowed branch, When it tries to assume the deploy role, Then AWS refuses it.
- **Budget alert (manual, product owner).** Given the budget alert email and thresholds (D-05, D-07), When the product owner creates the budget in the AWS console following the runbook in ADR-004, Then a monthly cost budget of about 20 USD exists with an email alert (at least at 80% actual and 100% forecast) to that address, the subscription email is confirmed, and this is verified by a screenshot or by the product owner confirming it in `status/`.
- **Done: deploy works from CI.** Given the CI deploy role, When the GitHub Actions workflow runs on `main`, Then it assumes the role and `cdk deploy` of the "hello" stack to `prod` in `eu-west-1` succeeds, with no stored AWS secrets.
- **Infra as code.** Given the OIDC provider and the CI roles, When they are created, Then they are defined in IaC (CDK or a documented one-time bootstrap template in the repo), so they can be recreated; the budget and any other manual console step are written in the runbook.

## Design notes (Architect)
- ADRs / contract sections affected: ADR-004 (one account, `prod` only, `eu-west-1`, `tco-cars` local access and local deploy rules before v1.0.0 (D-13), CI deploy role and read-only PR diff role, budget runbook, prod approval gate and read-only agent access from v1.0.0).
- No AWS Organizations or IAM Identity Center in this story; both are on the ADR-004 v1.0.0 checklist.
- Architect reviews the trust policies and role permissions before the Tester verifies.

## Test notes (Tester)
- Verify each acceptance criterion: search repo/CI for keys, attempt role assumption from a disallowed ref (expect denial), confirm the `tco-cars` profile returns the expected account and can run `cdk diff` and `cdk deploy` locally (no read-only denial test before v1.0.0), confirm the `deploy-local` wrapper refuses a dirty tree and an unpushed commit, confirm a direct push to `main` is rejected, confirm the budget via the product owner's screenshot or confirmation, observe one CI deploy of "hello" to `prod`.

## Out of scope
- AWS Organizations / Control Tower landing zone beyond what ADR-004 needs.
- Custom domains, Route 53, ACM certificates.
- Budget alert in CDK (it is a manual step by the product owner).
- Cost dashboards beyond the single budget alert.
- The v1.0.0 prod approval gate and feature flags (designed by the Architect before v1.0.0).

# S0-6: Connect the AWS account (secure access, bootstrap, OIDC, budget)

**Epic:** Sprint 0 foundations · **Size:** M · **Owner:** Developer (design: Architect; access: product owner) · **Status:** Backlog
**Requested by:** product owner

**Dependencies:**
- **S0-2 / ADR-004** must decide the account and stage layout (one account with `dev`/`prod` stages vs. separate accounts), the region and the CI auth model first.
- S0-3 Part A (a CDK app with a "hello" stack and a CI workflow to run it).
- Product owner supplies: AWS account ID(s) (D-01), an admin login for the one-time bootstrap (D-01), region choice (D-02), account layout preference (D-03), GitHub repo owner/name (D-04), budget alert email (D-05).
**Blocks:** S0-3 Part B (deploy step in CI).

## Story
As the Developer, I want secure local and CI access to the AWS account, so that I can deploy to `dev` from my machine and from GitHub Actions without any long-lived keys.

## Acceptance criteria
- **No long-lived keys.** Given the repo and the CI configuration, When they are searched (including git history and GitHub Actions secrets), Then there are no long-lived AWS access keys or secret keys; the only AWS-related values are non-secret identifiers (account ID, region, role ARN) as decided in ADR-004.
- **Local access.** Given a developer machine, When the developer signs in via AWS IAM Identity Center (SSO) or a named CLI profile with short-lived credentials (as chosen in ADR-004), Then `aws sts get-caller-identity` returns the expected account and the setup steps are documented in the repo (e.g. `docs/runbooks/aws-access.md`).
- **Admin login used once.** Given the product owner's admin login, When the one-time bootstrap is complete, Then day-to-day work no longer needs it, and the PM records in `status/` that it can be stored away or reduced.
- **Region bootstrapped.** Given the EU region chosen in ADR-004 (`eu-north-1` or `eu-central-1`), When `cdk bootstrap` has run for every account used by `dev` (and `prod`, if a separate account), Then the CDK bootstrap stack exists in that region only, and no resources are created outside the EU (except global services CloudFront needs).
- **OIDC with least privilege.** Given the GitHub repo owner/name, When the GitHub Actions OIDC identity provider and a deploy role are created, Then the role's trust policy only allows that repo (and the branch/environment set in ADR-004, e.g. main for `dev`), and its permissions are limited to what CDK deploy needs (assuming the CDK bootstrap roles), not `AdministratorAccess`.
- **OIDC is denied for others.** Given a workflow run from a fork, another repo or a non-allowed branch, When it tries to assume the deploy role, Then AWS refuses it.
- **Budget alert.** Given the budget alert email, When AWS Budgets is configured, Then a monthly cost budget of about 20 USD exists with an email alert (at least at 80% actual and 100% forecast) to that address, and the product owner has confirmed the subscription email.
- **Done: deploy works locally.** Given local credentials from the step above, When the developer runs `cdk deploy` for the `dev` stage, Then the "hello" stack deploys successfully to the chosen region.
- **Done: deploy works from CI.** Given the OIDC deploy role, When the GitHub Actions workflow runs on the allowed branch, Then it assumes the role and `cdk deploy` of the "hello" stack to `dev` succeeds, with no stored AWS secrets.
- **Infra as code.** Given the OIDC provider, deploy role and budget, When they are created, Then they are defined in IaC (CDK or a documented one-time bootstrap template in the repo), so they can be recreated; any manual console step is written in the runbook.

## Design notes (Architect)
- ADRs / contract sections affected: ADR-004 (account/stage layout, region, local access method, OIDC role per stage, prod approval gate). If separate accounts are chosen, this story covers `dev` fully and sets up `prod` bootstrap only; prod deploys stay behind product owner approval.
- Architect reviews the trust policy and role permissions before the Tester verifies.

## Test notes (Tester)
- Verify each acceptance criterion: search repo/CI for keys, attempt role assumption from a disallowed ref (expect denial), confirm the budget exists with the right threshold and email, observe one local and one CI deploy of "hello" to `dev`.

## Out of scope
- AWS Organizations / Control Tower landing zone beyond what ADR-004 needs.
- Custom domains, Route 53, ACM certificates.
- Production deploy (needs product owner release approval).
- Cost dashboards beyond the single budget alert.

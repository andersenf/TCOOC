# S0-3: Scaffold repo, CDK app and CI pipeline; deploy "hello" to prod

**Epic:** Sprint 0 foundations · **Size:** M · **Owner:** Developer (review: Architect) · **Status:** Backlog

**Dependencies:**
- Part A (scaffold, lint, test, synth): ADR-001 and ADR-004 from S0-2.
- Part B (deploy step): **S0-6 done** (AWS account bootstrapped, OIDC deploy role available).
**Blocks:** all Sprint 1 build stories.

## Story
As the Developer, I want a scaffolded monorepo with a CDK app and a CI pipeline that deploys to `prod`, so that every later story ships as a small PR that deploys cleanly.

## Acceptance criteria
### Part A: scaffold and CI checks (no AWS access needed)
- Given a fresh clone, When the Developer runs the documented install and check commands, Then lint (ESLint + Prettier), TypeScript strict type-check and unit tests (Vitest, with at least one placeholder test) all pass.
- Given the repo layout from ADR-001/ADR-004, When it is scaffolded, Then it contains a frontend SPA skeleton (TypeScript + Vite), an API Lambda skeleton, `src/backend/config/dk/` (empty or placeholder with `TODO-VERIFY`), `tests/oracle/` and a CDK app with frontend, api and data stacks parameterised by stage.
- Given a pull request, When GitHub Actions runs, Then lint, type-check, unit tests and `cdk synth` run and the PR is blocked if any fails.
- Given the repo, When it is searched, Then it contains no AWS access keys, secrets or account-specific credentials (account ID/region come from config or CI variables as decided in ADR-004).

### Part B: deploy step (after S0-6)
- Given a merge to the main branch, When the pipeline runs, Then it assumes the `prod` CI deploy role via OIDC (from S0-6) and runs `cdk deploy` for the `prod` stage without manual steps.
- Given a successful deploy to `prod`, When a user opens the CloudFront URL, Then they see a "hello" page in Danish (with English available via the i18n setup), and the page calls a "hello" API endpoint through API Gateway → Lambda and shows its response.
- Given the deploy, When it finishes, Then the `prod` URL is printed in the pipeline output and recorded in `status/sprint-00-status.md` by the PM.
- Before v1.0.0, a merge to main deploys to `prod` with no approval gate; PR checks must pass first.

## Design notes (Architect)
- ADRs / contract sections affected: ADR-001, ADR-004. Architect reviews the PR for conformance.
- Part A and S0-6 can overlap; only Part B waits for S0-6.

## Test notes (Tester)
- Oracle cases / edge cases: Tester verifies the "hello" smoke test in `prod` (page loads, API responds, DA/EN toggle works) and that a failing lint or test blocks the PR.

## Out of scope
- Real endpoints, DynamoDB tables with data, ingestion jobs.
- Custom domain names and TLS certificates for a custom domain.
- Playwright E2E suite (harness only, if cheap; full suite is Sprint 1+).

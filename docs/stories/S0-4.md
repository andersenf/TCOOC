# S0-4: Write the 12 oracle cases and set up the test harness

**Epic:** Sprint 0 foundations (feeds E3) · **Size:** M · **Owner:** Tester · **Status:** Backlog

**Dependencies:** `docs/02-tco-model-dk.md` v0.2 (available now). The harness runner depends on S0-3 Part A (repo + Vitest). Final sign-off depends on the product owner approving TCO model v0.2 (D-09).
**Blocks:** E3 TCO engine stories (Sprint 1).

## Story
As the Developer of the TCO engine, I want hand-worked oracle cases with expected results per year, so that I can write the calculation tests first and prove the engine matches the model within ±1 DKK.

## Acceptance criteria
- Given the oracle list in `docs/02-tco-model-dk.md`, When S0-4 is done, Then `tests/oracle/` contains at least 12 cases: EV vs. petrol (defaults, `Y = 4`), EV vs. diesel, low km (8,000), high km (30,000), short (`Y = 1`), long (`Y = 10`), PHEV vs. petrol, used EV (`A0 = 3`) vs. used diesel, the km line binding from high km/year, a used car with high `O0` (km line binds at purchase), a car that reaches `Kmax` inside the period (value 0 from then on), and a PHEV using the 250,000 km limit vs. a petrol car using 400,000 km.
- Given each case, When it is read, Then it lists every input for both cars (including `O0` and `Kmax`), and the expected `O(y)`, `W(y)`, `R(y)`, `Running(y)` and `C(y)` for every year `y = 0..Y`, plus `TCO(Y)`, TCO per year and cost per km.
- Given the residual-value rule `W(y) = min(V(A0 + y), max(0, 1 − O(y)/Kmax))` with `R(y) = (P / W(0)) × W(y)`, When the cases are reviewed, Then the set shows at least: a year where `V` binds, a year where the km line binds, `R(0) = P` for every case, and `R(y) = 0` once `O(y) ≥ Kmax` (including `O(y) = Kmax` exactly, in a case or an extra edge case).
- Given the edge rules, When the cases are reviewed, Then at least one case or extra edge case covers each of: `K = 0` (cost per km shown as "—"), a new car with a small `O0 > 0` (`P_new` slightly above `P`), a `V(a)` value between config points (linear interpolation) and beyond the last point (hold last value), and rejected inputs (`O0 ≥ Kmax`; `condition = new` with `O0 > 1,000` or `A0 ≠ 0`; `Y` outside 1..10).
- Given the rates and `V` points in the model are `TODO-VERIFY`, When the cases are written, Then each case states the assumed rates, `V` points and `Kmax` explicitly in the case file, so that the cases stay valid when real config values arrive (cases test the formulas, not today's tax rates).
- Given the harness, When `npm test` (or the documented command) runs, Then it loads every oracle case, runs it against a calculation function interface (stubbed until E3), and reports each case; the comparison tolerance is ±1 DKK (100 øre).
- Given an oracle case where the model is ambiguous, When the Tester hits it, Then the question is logged to the PM (not guessed) and listed in `status/decisions-needed.md` if only the product owner can resolve it.

# S0-4: Write the 9 oracle cases and set up the test harness

**Epic:** Sprint 0 foundations (feeds E3) · **Size:** M · **Owner:** Tester · **Status:** Backlog

**Dependencies:** `docs/02-tco-model-dk.md` v0.1 (available now). The harness runner depends on S0-3 Part A (repo + Vitest). Final sign-off depends on the product owner approving TCO model v0.1 (D-09).
**Blocks:** E3 TCO engine stories (Sprint 1).

## Story
As the Developer of the TCO engine, I want hand-worked oracle cases with expected results per year, so that I can write the calculation tests first and prove the engine matches the model within ±1 DKK.

## Acceptance criteria
- Given the oracle list in `docs/02-tco-model-dk.md`, When S0-4 is done, Then `tests/oracle/` contains at least 9 cases: EV vs. petrol, EV vs. diesel, low km (8,000), high km (30,000), short (3 years), long (10 years), PHEV vs. petrol, used EV (`A0 = 3`) vs. used diesel, and a financed purchase (`L > 0`, `N ≠ Y`).
- Given each case, When it is read, Then it lists every input for both cars, and the expected `R(y)`, `Running(y)`, `Interest(y)` and `C(y)` for every year `y = 0..Y`, plus `TCO(Y)`, cost per km, `B(Y)` and the expected break-even result.
- Given the break-even rules, When the cases are reviewed, Then the set covers at least: a break-even inside `1..Y`, "no break-even within Y years", and "same purchase price".
- Given the edge rules, When the cases are reviewed, Then at least one case or extra edge case covers each of: `K = 0` (cost per km shown as "—"), `r = 0` with `L > 0`, `N < Y` (interest stops after year `N`, `B(Y) = 0`), `N > Y` (`B(Y) > 0`, not added to TCO), and a `V(a)` value between config points (linear interpolation) and beyond the last point (hold last value).
- Given the rates in the model are `TODO-VERIFY`, When the cases are written, Then each case states the assumed rates explicitly in the case file, so that the cases stay valid when real config values arrive (cases test the formulas, not today's tax rates).
- Given the harness, When `npm test` (or the documented command) runs, Then it loads every oracle case, runs it against a calculation function interface (stubbed until E3), and reports each case; the comparison tolerance is ±1 DKK (100 øre).
- Given an oracle case where the model is ambiguous, When the Tester hits it, Then the question is logged to the PM (not guessed) and listed in `status/decisions-needed.md` if only the product owner can resolve it.
